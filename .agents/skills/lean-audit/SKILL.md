# Lean Audit（Lean 形式化审计）

严格执行 `AGENTS.md` 的形式化纪律，区分“作者自报”与“本机实测”，完成构建与公理依赖分层审计。

## 执行流程

1. **区分“论文自报”与“实测”**
   - 在实际构建与运行检查前，所有论文或文档中宣称的形式化结果一律标注为「**作者自报，未复跑**」。
   - 严禁直接复述历史日志或论文中的 jobs 数与公理清单当作当前实测结果。

2. **实际构建与导出公理依赖**
   - 若当前环境具备 Lean/Lake 工具链，进入目标 Lean 项目目录实际执行：
     - 全量或目标模块构建（如 `lake build`）
     - 零写入单文件/审计检查（如 `lake env lean Audit.lean`）
     - 逐声明导出 `#print axioms <声明名>` 原始输出，并检索全项目是否存在 `sorry` / `sorryAx`。
   - 优先用 lean-lsp-mcp 工具链完成同一审计：`lean_build`（构建并重启 LSP）、`lean_diagnostic_messages`（跑诊断，`category: 'sorry'` 即未证声明）、`lean_verify`（按全限定名导出每个关键定理的公理依赖与最坏公理类别）；与 CLI 途径至少执行其一，两种途径都执行时若结果不一致必须复核。
   - 只有实测通过且无 `sorryAx` 后，才可改称「**已核实**」。若环境不可构建，必须明确说明受阻原因并保持「未复跑」状态。

3. **公理依赖分层列表**
   将 `#print axioms` 输出严格分为三层列示：
   - **Lean 基础公理**：`propext`、`Classical.choice`、`Quot.sound`
   - **经典白名单公理**：如 `e_transcendental`、`pi_transcendental`、`mu_e_eq_two` 等公认经典定理
   - **项目自加公理**：任何其余公理（含未独立核验的预印本公理或缺失基础定理的公理化输入），必须逐条标出并注明下游影响范围。

4. **形式化“首创”声称口径**
   - 对“某定理首次在 Lean 中形式化”类声称，**只认「未找到先例的负搜索」口径**（说明检索过的 mathlib 版本、formal-conjectures、Archive 等范围），绝不允许绝对化表述为“全球首创/不存在先例”。

## 输出格式
遵循 `AGENTS.md`：先给**一句总判断**，再给对照表（`结果 | 类别 | 核查状态 | 与已有文献关系 | 依据`），并附实测命令、退出码、`sorryAx` 计数与三层公理清单。
